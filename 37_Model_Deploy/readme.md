## 一、部署总览

### 1.1 推理框架是什么？为什么不能拿训练框架跑推理？

推理框架是面向线上服务、专门把训好的模型高效执行起来的软件栈，里面有图优化、算子库、内存管理、运行时调度这几层，目标就是尽量榨干硬件算力。

不用 PyTorch 这类训练框架跑推理，有三个理由。它带着自动求导、优化器状态、梯度通信这些推理完全用不上的东西，白占内存和启动时间；它的算子实现优先照顾通用性和易用性，不是访存效率和批处理吞吐，同一个模型在专门框架上快好几倍是常态；它还缺服务化能力，动态批处理、请求排队、KV Cache 复用、优雅降级、可观测性，这些训练框架一概没有。

### 1.2 推理框架一般包含哪些模块？

四块，各自解决不同的问题。

图优化模块对付计算冗余和低效的计算图，典型手段是算子融合，把 Conv+BN+ReLU 合成一个内核，免得中间结果反复读写显存。算子库模块对付单个算子执行效率低，同一个矩阵乘法写法不同性能能差好几倍，它负责为每种硬件和形状提供调过优的内核。内存管理模块对付分配开销和显存碎片，靠池化和张量生命周期分析，把运行时的动态申请变成启动时的一次性分配。运行时调度模块对付执行顺序和请求调度，决定多个请求怎么组批、计算和数据传输怎么重叠、流式输出什么时候吐。

四者的配合逻辑很朴素：图优化减少工作量，算子库加快单项，内存管理降低开销，调度让硬件不空转。

### 1.3 推理优化的三个方向是什么？

少算、快算、省内存。

少算指的是减少不必要的计算，算子融合、常量折叠、剪枝、蒸馏、跳过冗余层都算。快算是让硬件更高效地执行同样的计算，用调优过的算子内核、换更合适的数据精度、减少访存、把计算密集的部分塞进 Tensor Core。省内存是降低显存占用，量化、KV Cache 分页与压缩、显存复用。

顺序上我一般先少算、再省内存、最后快算。前两步是降低问题规模，第三步才是用更好的工具解决同一个问题。反过来做容易在一个本来能规避的计算上花大力气优化，投入产出比很差。

### 1.4 传统模型推理和大模型推理差在哪？

差在算术强度，也就是 FLOPs 除以访存量。

传统 CV 模型是计算密集的，单次推理要处理几十万像素、卷积核反复复用，每读一个字节能做很多次浮点运算，所以加大 batch 能明显提吞吐。大模型自回归生成反过来，是访存密集的：每生成一个 token 都要把全部权重从显存读一遍，实际计算量却很小。7B 模型生成一个 token 大约 140 亿次浮点运算，但要读约 14GB 权重，算术强度低得可怜，瓶颈落在显存带宽上。

这解释了一个现象：传统模型靠堆 batch 提吞吐，而大模型的 decode 阶段加 batch 几乎不增加时间成本，因为权重只读一次就能服务整批。Continuous Batching 的价值就在这儿。

### 1.5 Prefill 和 Decode 为什么要分开讨论？

因为两者的瓶颈根本不同。

Prefill 处理整个输入 prompt，所有 token 的注意力可以并行算，是一次大规模矩阵乘法，属于计算密集，算力是瓶颈。Decode 每次只生成一个 token，必须等上一个算完才能算下一个，没法并行，而且每步都要读全部权重，属于访存密集，显存带宽是瓶颈。

这个差异带来几条工程结论。两个阶段的最优 batch 策略不同，可以用 chunked prefill 把长 prompt 切片，与 decode 交错执行，别让长 prompt 把 decode 请求全堵住。优化手段也得分开看，提算力主要加速 Prefill，提显存带宽利用率主要加速 Decode。用户体验指标同样要分开定义，首 token 时延由 Prefill 决定，每 token 时延由 Decode 决定，这两者常常此消彼长。

### 1.6 显存墙是什么？显存被谁吃了？

显存墙指的是推理性能不再受算力限制，而是被显存容量卡住。显存一不够，要么降 batch、要么降并发、要么模型根本加载不进来。

显存被三部分吃掉。模型权重是静态的，7B FP16 约 14GB，不随负载变化。KV Cache 是动态的，随并发序列数乘序列长度线性增长，这部分最需要精细管理。还有 Prefill 时的激活和临时缓冲，随 batch 和序列长度增长。

KV Cache 的估算公式是 `2 × 层数 × KV 头数 × head_dim × 序列长度 × 并发数 × 每元素字节数`。拿 7B 举例（32 层、32 头、head_dim 128、FP16），单个 token 的 KV Cache 约 512KB，4000 token 上下文就占 2GB；并发 32 路就是 64GB，比模型权重本身还大。这就是为什么 KV Cache 管理是大模型推理最核心的工程问题。

### 1.7 为什么说显存带宽比算力更卡脖子？

因为 decode 阶段每生成一个 token 就要把整套权重从显存读一遍，而计算量相对于读取的数据量微不足道。

拿 7B 算笔账：FP16 权重约 14GB，一块带宽 2TB/s 的卡把它读完要 7ms 左右，这意味着每 token 时延的下限约为 7ms，约合 140 token/s，算力再强也突破不了，除非减少要读的数据量。

这条推理直接给出两个优化方向。一是减少读取量，量化把 FP16 换成 INT8 就等于把读取量减半、时延上限翻倍，剪枝和稀疏化同理。二是摊薄读取成本，提高 batch 让一次权重读取服务更多序列；或者用投机解码，一次前向验证多个 token。想清楚瓶颈在读不在算，大模型推理优化的很多设计就顺理成章了。

### 1.8 同一个模型换个框架性能差几倍，正常吗？

正常，而且很常见。

差异来自三个层次。算子实现质量上，attention 这类内存密集型算子，手写的融合内核能避免把中间矩阵写出到显存，跟朴素实现差出一个数量级。图优化程度上，有没有做算子融合、有没有针对特定形状特化，直接决定访存次数。调度与批处理策略上，有没有 Continuous Batching、有没有前缀复用、调度器会不会造成气泡。

还有两个常被低估的因素：框架版本（一次大版本重构可能带来 2-5 倍吞吐变化）和硬件绑定程度。通用框架追求可移植性，厂商自研框架做深度特化，在自家卡上通常更快但换卡就废。所以选型不能只看框架名，必须在自己的模型形状和自己的硬件上实测。

### 1.9 怎么判断一个模型能不能部署？

六个维度。

算子兼容性，把模型算子清单跟目标后端支持列表对一遍，列出只能跑回退实现的算子，这些往往是性能杀手。动态性，模型对输入形状的依赖越强越难做图优化，大模型还要看 KV Cache 的建模方式。精度要求，业务能容忍多大数值误差，这决定量化方案。资源预算，目标硬件的显存、算力、功耗、发热限制，反推最大可部署规模和并发。时延与吞吐目标，明确首 token 时延、每 token 时延、P95 和 QPS，这是选框架和批策略的依据。可维护性，要不要热更新、多模型共存、灰度切换、监控上报。

最容易翻车的是算子兼容性和精度要求。很多项目是模型训完才发现有算子不支持，或者量化后精度掉出业务阈值。所以可行性评估应该在模型选型阶段就做，不是训完再做。

## 二、中间表示与模型格式

### 2.1 ONNX 是什么？为什么能当桥梁？

ONNX 是一个开放的神经网络中间表示格式，用统一的方式描述计算图。

它能当桥梁，是因为把模型描述和执行引擎解耦了：上游只要把模型导成 ONNX，下游各种推理后端各自去支持这个格式。这样 M 个训练框架和 N 个推理后端之间只需要 M+N 次适配，不是 M×N 次，工程成本降下来一大截。

两点要强调。ONNX 本身不是运行时，它只描述模型不执行，执行靠 ONNX Runtime 这些东西。它也不是性能保证，只统一了表示，性能取决于下游后端做了多少优化。

### 2.2 ONNX 文件里都有什么？

四个核心元素。

Graph 是整张计算图的顶层容器，含节点、输入输出和张量定义。Node 是算子实例，声明算子类型、输入输出张量名和属性（stride、padding 这些），节点之间靠张量名互相连接构成有向无环图。Tensor 是数据容器，分图输入输出和中间结果。Initializer 是初始值，也就是训练得到的权重，随模型一起序列化进文件。

另外还有 Opset 作为整张图的语义约定，以及 value_info 之类的形状标注。理解这套结构最实用的价值是：导出出错时能直接打开 ONNX 看节点连接对不对，比在黑盒里猜高效得多。

### 2.3 Opset 为什么会引发兼容问题？

Opset 是一组算子定义的版本号，它约定这个模型里的算子按哪一版语义解释。兼容问题有三个来源。

后端支持的 Opset 范围有限，每个推理框架只实现了部分 Opset，导出的版本太新就直接报"不支持的算子"。同一算子在版本间语义会变，某些采样算子的坐标对齐方式、antialias 行为在不同 Opset 下不一样，同一份权重在不同 Opset 下会输出不同结果，这是最隐蔽的一类问题，不报错但结果错。新模型结构依赖新算子，旧 Opset 里根本没定义。

选型上先用后端明确支持的 Opset 版本导出，导出后用测试样本做数值比对，算原框架输出和 ONNX Runtime 输出的最大绝对误差，超过阈值就降 Opset 或者用插件算子替代。

### 2.4 ONNX 有哪些做不到的事？

有几件事它做不到，而且都不是能绕过去的。

不是所有算子都能导出。动态控制流（依赖张量值的 if/while）、自定义算子、部分动态形状语义在导出时会失败或退化成慢实现，大模型里的动态 shape 和 KV Cache 管理更是经典痛点。图级优化能力有限，只提供有限的标准优化 pass，没有 TensorRT 那种针对硬件的自动调优。不保证性能，它只保证可移植，ONNX Runtime 的 CPU 执行有时甚至比原生 PyTorch 还慢。版本适配成本高，模型、Opset、后端三者的版本组合要反复试。

大语言模型推理基本不用 ONNX，业界都改用专门的大模型推理框架，因为 LLM 的动态 shape、KV Cache、Continuous Batching 超出了 ONNX 的设计假设。

### 2.5 ONNX 导出的标准流程和常见坑？

五步。

导出前把模型切到 `eval()` 模式（否则 BatchNorm 和 Dropout 行为不一致）、移到目标设备、准备 shape 合法的示例输入、确认输入输出命名清楚、必要时用 wrapper 把复杂输出拆扁平。然后调导出接口，指定 Opset、动态轴和是否做常量折叠。接着查看图，检查节点连接，看看有没有出现大量 `Loop`/`If` 这类降级算子、有没有意外的 `Cast`。然后做数值验证，用同一批输入跑原模型和 ONNX Runtime，比对最大绝对误差和相对误差。这一步必须做，跳过等于把风险留到线上。最后在目标后端上测时延吞吐，确认优化生效。

常见坑有四个：动态 shape 处理不当导致只支持固定 batch；Opset 语义变更导致数值偏差；训练推理模式没切换导致结果不稳定；大模型 shape 过多导致后端编译时间爆炸。

### 2.6 ONNX、TorchScript、TensorRT Engine、OpenVINO IR 怎么选？

四者定位不同。

ONNX 是跨框架的开放中间表示，最大价值是可移植性，不绑定厂商。TorchScript 是 PyTorch 生态内的部署表示，优势是无缝衔接 PyTorch 代码，可以直接导出带控制流的模型，跨出生态后支持就有限了。TensorRT Engine 是 NVIDIA GPU 上的最终优化产物，它不是中间表示而是经过算子融合、精度校准、内核自动调优后生成的可执行引擎，性能最好但必须和 GPU 架构、驱动、TensorRT 版本严格匹配，换环境就得重建。OpenVINO IR 面向 Intel 硬件，针对自家平台做了深度特化。

一句话原则：要跨平台用 ONNX，留在 PyTorch 生态用 TorchScript，只要极致性能且锁定 NVIDIA 就用 TensorRT，跑 Intel 平台用 OpenVINO。

### 2.7 为什么非要有个中间表示？

值得为它多一道工序的原因有几个。

解耦训练与推理。研发团队可以用任意框架、任意版本训练，部署团队只消费一种格式，避免"训练环境和生产环境必须完全一致"这种脆弱约束。便于生产优化。有了显式的计算图，才能做图级的融合与重写；训练框架的动态图是逐算子解释执行的，看不到全局结构，也就没有整体优化空间。降低依赖与跨平台成本。交付一个自包含的模型文件，而不是一段 Python 代码加一堆 pip 依赖加特定版本的框架，在客户现场部署、边缘设备部署、需要长期维护的老项目里都很关键。

需要动态控制流、频繁变化的模型，以及大语言模型这类超出现有中间表示设计假设的负载，不适合走这条路。还有一点要记住：中间表示是可优化的前提，不是优化的结果。

## 三、大模型推理机制

### 3.1 KV Cache 是什么？为什么又省时间又吃显存？

自回归生成时，第 t 个 token 的注意力要用到前面所有 token 的 K 和 V。不缓存的话，每生成一个 token 就要把整段上下文重算一遍，总计算量是 O(n²)，越往后越慢。

KV Cache 把每一步算出的 K、V 存下来复用，每步只需要算新 token 对应的那一行注意力，复杂度降到 O(n)。

代价是显存，缓存大小与序列长度、并发数、层数、头数、head_dim 成正比，而且不随生成过程释放。这是典型的用显存换时间，所以所有 KV Cache 优化（分页、量化、淘汰策略、前缀共享、MQA/GQA 减头数）本质都是在显存和速度之间重新找平衡点。

### 3.2 PagedAttention 到底在解决什么？

在它之前，KV Cache 按每个序列独占一段连续显存来分配，有三类浪费。

内部碎片，预留了最大长度的空间但实际用不满，长尾序列浪费大量空间。外部碎片，反复申请释放后显存被切碎，大块连续空间申请不到。无法共享，多个请求如果前缀相同，K、V 内容也相同，却各占一份。

PagedAttention 照搬操作系统的虚拟内存分页：把 KV Cache 切成固定大小的 block，序列的 block 在物理显存上可以不连续，再用一张 block table 记录逻辑块到物理块的映射。这样显存按需分配几乎没有碎片，更关键的是多个序列可以共享同一个物理块，前缀相同的请求直接指向同一份 block，这就成了自动前缀缓存。同样的卡能支持更大的 batch 和更高的吞吐，这是 vLLM 早期能打出数倍吞吐差距的主要原因。

### 3.3 Continuous Batching 和静态批处理有什么不一样？

静态批处理把一批请求同时开始、同时结束，整批必须等最长的那个序列生成完才能交付。

问题在于大模型生成的序列长度差异极大，有人问一句话，有人要写两千字，短请求完成后对应的计算资源只能空转等待，GPU 利用率被木桶短板拖死；而且新请求必须排队等下一批，时延很高。

Continuous Batching（也叫 in-flight batching）改成每次解码迭代重新组批：某个序列生成到 EOS 就立即退出，空出的槽位马上填入排队中的新请求。硬件始终在处理当前所有活跃序列，利用率接近饱和。在长短请求混合的真实负载下，吞吐相比静态批处理常有数倍提升，排队时延也明显下降，因为新请求不用等下一批开始。这已经是现在所有主流大模型推理框架的标配。

### 3.4 调度器每一轮在做什么决策？

四类决策。

谁进入这一轮，从等待队列里挑哪些请求参与本轮计算。Prefill 和 Decode 怎么配比，Prefill 请求会占用大量算力，一次塞进多个长 prompt 会让正在解码的请求长时间阻塞，用户看到的就是卡住不动，所以要用 chunked prefill 把长 prompt 切成小块与 decode 交错执行。KV Cache 怎么分配和淘汰，显存不够时选择抢占谁，通常优先抢占最后到达的请求，因为它的前缀缓存价值最低、重算代价小。批大小的上界，batch 越大吞吐越高但单请求时延会变差，得在 SLO 约束下取折中。

这些决策存在明显冲突。吞吐、首 token 时延、每 token 时延三者不可能同时最优，所以调度策略本质上是面向业务 SLO 的一套取舍规则，不是追求某个单点指标的极值。

### 3.5 前缀缓存能省多少算力？

多个请求的开头部分如果完全相同（系统提示词、few-shot 示例、同一份长文档、多轮对话历史），这段前缀的 KV Cache 就是一致的，可以复用不必重算。

实现上通常用一棵前缀树组织已缓存的 token 序列，新请求进来先做最长前缀匹配，命中的部分直接挂载已有 block，只对没命中的后缀做 Prefill。

收益最大的场景有四类：固定的长系统提示词，几千 token 的角色设定占成本大头；同一份文档的多次提问，RAG 里对同一篇长文连续追问；多轮对话，每轮都带着完整历史；Agent 循环，每步都重发相同的工具定义和历史。这类优化的性价比极高，不损失质量、不需要训练、只是省掉重复计算，上线必做。它依赖分页机制才能实现物理共享，这也是 PagedAttention 的额外价值。

### 3.6 投机解码为什么能加速？

思路是用一个小草稿模型先连续猜出 k 个 token，然后让大模型一次前向并行验证这 k 个 token，保留从头开始连续正确的部分，遇到第一个错误就重新采样并从那里继续。

它不改变输出分布，因为验证步骤用了拒绝采样，只有大模型认为草稿 token 概率足够高时才接受。加速来源是用并行计算换串行步骤：大模型原本需要 k 次串行前向，现在只需要 1 次，而 decode 阶段本来就是访存密集、算力大量闲置，验证 k 个 token 的额外算力成本很小，正好把闲置算力用起来。

限制也很明确，加速比取决于草稿模型的命中率。任务难、草稿模型猜不准时接受率低，反而增加了开销。所以工程上一般选择同族且小得多的草稿模型，或使用不额外训练草稿模型的自投机方案。

### 3.7 MQA 和 GQA 是怎么把 KV Cache 压下来的？

标准多头注意力里 K 和 V 的头数与查询头数相同，所以 KV Cache 大小正比于头数。

MQA 让所有查询头共享同一组 K、V，KV Cache 直接缩到 1/头数，32 头就缩 32 倍。GQA 是折中，把查询头分组、每组共享一组 K、V，比如 32 个查询头分 8 组，KV Cache 缩到 1/4，兼顾显存和表达力。

收益有两层：同样显存能支持更大 batch 或更长上下文；decode 时每次要读的 KV 数据变少，访存带宽压力直接下降，每 token 时延降低。代价是注意力表达能力减弱，但实践中 GQA 的损失通常可忽略，所以成了现代模型的默认选择。这也说明部署成本会反向影响模型架构设计。

### 3.8 长上下文部署会多出哪些麻烦？

麻烦比短上下文多不少。

KV Cache 爆炸，显存占用与上下文长度线性增长，128K 上下文的 KV Cache 能到数十 GB，直接决定单卡能承载多少并发。Prefill 时延剧增，首 token 时延随 prompt 长度增长，用户可能等十几秒才看到第一个字，对策是 chunked prefill、把长文档预处理成缓存、或者给长上下文请求单独分配资源池。注意力质量衰减，即使显存扛得住，模型对中段信息的利用仍然不佳，所以"支持 128K"和"能有效用 128K"是两回事。调度复杂度上升，长请求会长时间占用资源，容易造成短请求饥饿。

工程对策可以概括成三句：能用缓存就别重算，能不喂那么多就少喂，必须喂就分级处理。

## 四、框架与选型

### 4.1 开源大模型推理框架有哪些？

vLLM 是通用高吞吐框架，靠 PagedAttention 和 Continuous Batching 起家，易用性和生态最好，社区迭代快，一般拿它当起点。SGLang 在结构化生成（约束解码、JSON 输出）和前缀复用上做得最强，适合 Agent 与固定模板类负载。TensorRT-LLM 是 NVIDIA 官方的，追求单卡单机极致性能，做深度算子特化和量化支持，代价是构建流程重、与硬件版本强绑定。LMDeploy 是一站式方案，覆盖量化、推理、服务化，国内用得不少。

轻量本地部署有 Ollama 和 llama.cpp，牺牲吞吐换开箱即用和低资源占用，适合个人开发与端侧。信创场景还有昇腾的 MindIE 这类厂商自研栈，那里基本是刚需。

### 4.2 框架选型看什么？

五个维度，按重要性排。

硬件匹配排第一，目标卡是什么往往一票否决，国产卡通常只能用厂商自研栈。接着是吞吐与时延的实测表现，必须用自己的模型形状和真实请求长度分布压测，框架宣传的数字一般是最优形状最大 batch 下测的，跟你的负载可能差很远。然后是功能完备度，连续批处理、前缀缓存、结构化输出、LoRA 热插拔、多模态输入、流式输出，缺一项就得自己补，成本可能超过性能收益。再是量化支持，支持哪些格式、量化能不能带来真实的端到端收益、精度损失是否可接受。最后是运维友好度，部署复杂度、依赖治理、可观测性、升级回滚难度、社区活跃度。

我的经验是性能差距在其次，能不能稳定运维才是长期成本的大头。很多项目最终选的是第二快但最好维护的那个。

### 4.3 为什么大模型不能复用传统推理框架的能力？

三处不匹配。

动态 shape 上，传统框架最强的是固定形状加图优化，可以离线把算子融合、内核调优做到极致，但大模型的序列长度和 batch 每次都变，图无法静态确定，优化链条直接失效。KV Cache 管理上，传统推理是一次前向结束就释放中间结果、完全无状态，而 KV Cache 是跨步骤、跨请求、有复用价值的持久状态，需要分页、共享、淘汰这套全新机制，传统框架的内存模型里没这个概念。请求调度上，传统框架处理独立无状态请求，批处理粒度是一批请求，大模型需要逐 token 迭代的调度，还要处理 prefill 和 decode 混合、抢占、流式输出，是完全不同的调度问题。

不过在固定形状、计算密集、无状态的场景里，传统框架仍然不可替代，CV 模型、小模型端侧推理上，TensorRT 和 OpenVINO 依旧是最优选择。

### 4.4 结构化生成是什么？为什么得框架支持？

结构化生成指的是解码的每一步只允许符合目标语法的 token 进入候选集，保证输出一定符合指定格式（JSON Schema、正则、枚举值）。

机制上是在 logits 上加一个掩码，把不符合当前语法状态的 token 概率置为负无穷，再正常采样。它必须由框架在解码循环里逐 token 干预，因为这属于运行时内部行为。光靠 prompt 说"请输出 JSON"只能提高概率，保证不了格式，也避免不了意外 token。

收益有三个：格式百分之百合规，下游直接解析，不用写容错重试；省 token，不用再靠详细的格式说明和示例去引导；降低时延，约束后的搜索空间变小。这也是 Agent 场景里 SGLang 这类框架受欢迎的直接原因，工具调用的参数必须能被程序解析，而不能只是"大概率能解析"。

### 4.5 传统推理框架有哪些？各自适合什么场景？

ONNX Runtime 跨平台通用，支持 CPU、GPU、多种加速器，最大优势是可移植性和生态，适合多平台交付、不想被厂商绑定的场景。TensorRT 在 NVIDIA GPU 上性能最强，适合固定形状、计算密集、延迟敏感的 GPU 服务。OpenVINO 在 Intel 平台（CPU、核显、NPU）最优，适合纯 CPU 服务器和 Intel 边缘设备。TVM 是编译器式方案，通过自动调优为各种后端生成算子，自研芯片适配价值高，但工程落地成本大。NCNN、MNN、TFLite 面向移动端和嵌入式，特点是轻量、无重依赖、支持 ARM NEON 这类指令集优化。

选择依据一句话：先看硬件平台，再看形状是否固定，最后算运维成本。

### 4.6 移动端和边缘端部署受什么限制？

限制挺多，而且互相牵制。

算力和内存双低，手机 NPU 算力比服务器 GPU 低两三个数量级，内存只有几 GB 还要和系统争用，端侧常驻模型大多在几百 M 到 3B 之间。功耗和发热，持续推理会让设备发烫触发降频，实测性能明显低于峰值，所以端侧看重的是持续性能而不是瞬时峰值。能耗约束，移动设备靠电池，没法像服务器那样用功耗换算力。部署与更新机制，模型要随 App 分发、受应用商店审核、有包体大小限制，用户设备上还无法回滚，版本和灰度机制必须做严。隐私与合规，端侧数据不出设备是优势，但也意味着无法上报原始数据做分析，评估与迭代手段受限。

这些约束反向影响模型设计，端侧偏好小模型加量化加结构化剪枝，并且越来越多采用端侧处理常规请求、云端处理复杂请求的分工。

### 4.7 边云协同怎么分工？

典型是三级：端侧跑轻量模型做唤醒、意图初判、简单问答和脱敏预处理，好处是零网络时延、隐私不出设备；边侧（门店服务器、工控机、车载算力）跑中等模型做常规推理，兼顾低时延与一定能力，还能做本地数据聚合；云侧跑大模型处理复杂推理和长上下文任务，能力最强但时延成本也最高。

取舍维度有三个：时延（端小于边小于云，网络往返是硬成本）、能力（云大于边大于端）、成本与隐私（端侧边际成本最低、隐私最好，但要承担端侧算力成本与模型分发成本）。

设计上的关键决策是路由策略。简单做法是按意图分类和输入长度路由，成熟做法是按置信度动态升级，端侧模型对自己的回答置信度低时才升级到云端。最容易犯的错是把边界划在"能力"上而不是"场景"上，结果大量请求被无谓地送到云端，成本失控。

### 4.8 上线前怎么做压测和容量规划？

压测有三个要点。

必须模拟真实输入分布，请求长度、输出长度、并发到达模式都按线上分布来，否则结论失真。用统一的短请求压出来的吞吐数字没有意义，真实负载里长请求会把指标拉垮一大截。指标要分层记录，首 token 时延、每 token 时延、端到端时延、吞吐、显存峰值、错误率与超时率，而且都要看 P50/P95/P99 分位数而不是均值。要找拐点而不是峰值，持续加大并发，观察时延开始非线性上升的那个点，那才是可用工作区间。超过它系统会进入雪崩区：排队导致超时，超时导致重试，重试加剧排队。

容量规划是反推的：从 SLO 出发（比如 P95 端到端不超过 3 秒、峰值 QPS 是 20），结合单请求平均输出 token 数和单卡实测吞吐算出需要的卡数，再乘 1.3 到 1.5 的安全系数应对突发。另外别忘留降级路径，过载时限制输出长度、切换小模型、关闭非核心功能，比直接超时体验好得多。

## 五、模型压缩

### 5.1 模型压缩有哪几大类？

五类。

量化降低数值精度，直接减少显存占用与访存量，性价比最高、落地最广。剪枝去掉不重要的权重或整个通道、层，减少参数量和计算量。知识蒸馏用大模型指导小模型训练，让小模型学到更平滑的分布，它属于训练方法，不是结构改造。低秩分解把大权重矩阵拆成两个小矩阵相乘。架构级设计是从模型设计阶段就用更高效的组件，分组卷积、深度可分离卷积、GQA、稀疏专家都算，严格说属于避免冗余而非事后压缩。

这几类可以叠加，但收益递减，而且精度损失会累积，需要逐个引入逐个验证。

### 5.2 量化是什么？PTQ 和 QAT 怎么选？

量化是用低比特整数表示浮点权重和激活。做法是为每个张量（或每个通道、每组）算一个缩放因子和零点，然后 `q = round(x / scale) + zero_point`，推理时反量化或者直接用整数指令计算。

PTQ 是训练后量化，模型训完后用一批代表性数据跑一遍统计激活范围，直接确定缩放因子。几小时就能完成，不需要训练基础设施，缺点是精度损失不可控。激活值的长尾分布会把量化范围撑大，大多数值被压缩到很少的档位上，掉点就明显。QAT 是量化感知训练，在训练过程中插入伪量化节点，让模型前向时感受量化的舍入误差、反向时用直通估计器传梯度，主动学习适应量化。精度损失小得多，大模型 INT8 基本可以无损，但需要完整训练流程，成本高。

选择上先试 PTQ，掉出业务阈值再上 QAT。大语言模型还有第三条路，就是下面的 GPTQ、AWQ 这一类。

### 5.3 GPTQ、AWQ、SmoothQuant 各自解决什么？

三个方法各解一个痛点。

GPTQ 逐层做量化，用二阶信息估计每个权重的重要性，逐列量化并即时补偿已量化权重造成的误差，让整层输出尽可能接近原值。它解决的是朴素 PTQ 误差累积的问题，主要量化权重，可以做到 4bit 而精度损失不大。AWQ 的核心洞察是激活值中有约 1% 的显著通道幅度极大、决定了大部分输出，量化它们损失最大，所以按激活分布对显著权重通道做保护性缩放，把量化误差转移到不重要的通道上。它比 GPTQ 更快更好实现，对指令微调模型更友好。SmoothQuant 解决的是激活值比权重更难量化这个不对称问题：权重分布平滑好量化，激活值有长尾极值；做法是把激活的量化难度数学等价地迁移到权重上，让两边都变得好量化，从而实现 W8A8。

有个工程要点：只量化权重主要省显存和带宽，加速的是 decode；量化激活才能用上整数计算单元，加速的是 prefill。两者收益方向不同，选型前先明确自己的瓶颈在哪。

### 5.4 量化掉点怎么评估、怎么补？

评估不能只看困惑度，得做三层验证。数值层比对与原模型的逐层输出相对误差，定位误差从哪一层开始放大。任务层跑业务评估集和通用基准，看关键能力是否掉出阈值。行为层检查有没有异常输出，乱码、重复、语言混用都算，量化有时会造成局部崩溃而不是整体降级。

分层诊断很重要。量化误差通常是个别层造成的，尤其是激活值分布极端的层和语言模型头附近的层，找到这些层保留 FP16 就能用很小代价换回大部分精度，这就是混合精度量化。

补偿手段有四种：混合精度、用更多更有代表性的校准数据（校准集必须覆盖真实输入分布，这是最容易被糊弄也最影响效果的一步）、分组量化、在量化前后插入轻量适配层。还有一条容易被忽略：量化后的模型必须重新跑安全与拒答评估，因为量化会不可预测地影响对齐行为，某些被 SFT 压下去的有害输出可能重新冒出来。

### 5.5 剪枝有哪些类型？为什么非结构化剪枝落不了地？

非结构化剪枝把单个权重置零，可以做到 90% 以上的稀疏率而精度损失不大，但落地极难。稀疏矩阵的存储需要额外的索引开销，通用硬件上的稠密矩阵乘法根本利用不了零元素，必须依赖专门的稀疏计算库或硬件特性，否则不但不加速反而更慢，索引开销加访存不规整。

结构化剪枝去掉整个通道、整行整列或整层，剪完就是一个更小的稠密模型，可以直接跑在任何硬件上、直接受益。代价是同样的稀疏率对精度伤害更大，因为可剪的粒度粗。

折中方案是半结构化稀疏，比如 2:4 稀疏，每 4 个权重里最多保留 2 个，既有固定模式便于硬件加速（较新一代 NVIDIA 硬件原生支持），又能达到不错的压缩比。我的建议是，除非有硬件支持，否则优先做结构化剪枝或者干脆换一个参数量更小的模型。很多项目在非结构化剪枝上花的时间，最后还不如换模型划算。

### 5.6 蒸馏的机制和温度参数是什么？

做法是让学生模型学教师输出的软标签，而不是只学硬标签。

硬标签只告诉你正确答案是哪个，软标签还给出错误答案之间的相对可能性，这个信息叫暗知识，它编码了教师对类间相似性的理解，所以用软标签训练的学生模型泛化更好、收敛更快。

温度 T 的作用是放大或平滑概率分布。softmax 里除以 T，T 大于 1 时分布变平滑，那些原本概率极低的错误类会提升到可被学习到的量级，暗知识才显现出来；T 等于 1 就退化成普通 softmax。训练时常用 2 到 8，推理时恢复为 1。

形式上有 logits 蒸馏和特征蒸馏两种，前者对齐输出分布通用性强，后者对齐中间层表示、需要维度匹配的投影层，对结构差异大的师生对比较难用。在部署语境下，蒸馏的价值是把大模型能力搬到能落地的小模型上，代价是需要教师推理大量数据。

### 5.7 低秩分解为什么现在没什么人用了？

它的思路是把大权重矩阵近似分解为两个小矩阵相乘，参数量从 `m×n` 降到 `r(m+n)`，秩 r 通过保留奇异值能量占比来定。这在 CNN 时代被广泛研究，尤其用于压缩全连接层和卷积核。

现在少人用，理由也不复杂。量化更简单也更通用，它不改变结构、不需要重新训练、收益直接，性价比明显更高。现代架构本身已经很小，注意力机制和深度可分离卷积这些设计已经消除了大量冗余参数，留给低秩分解的空间不多，强行分解掉点明显。大模型时代的主战场是 KV Cache 和权重精度，不是卷积核分解。

不过低秩思想没消失，LoRA 本质上就是"把微调增量约束为低秩"，只是用在训练侧而不是压缩侧。

### 5.8 压缩之后怎么保证能力不掉？

四步验收。

先建未压缩基线，在同一套评估集上跑原模型，记录每个维度的分数，不能只有一个总分。再分层评估压缩后模型，通用能力、业务能力、行为特征（格式遵循、拒答边界、多语言一致性）三类都要过，其中行为特征最容易被漏掉但风险最高。然后抽样人工看输出质量，分数不变不代表体验不变，压缩可能导致输出变短、变啰嗦、语言混用，这些用自动指标很难捕捉。最后做边界测试，专门测长尾输入（超长、异常字符、多语言混杂），压缩对长尾的伤害通常远大于对典型样本的伤害。

还有一条纪律：压缩手段不要一次性全部叠加，INT4 加剪枝加蒸馏一起上，出问题无法归因，精度损失还会非线性累积。正确做法是逐个引入每次验证，找到收益与损失的最优点就停下来。

## 六、自定义算子与性能调优

### 6.1 什么时候需要自己写算子？

自定义算子是用底层语言（CUDA、Triton、C++）手写实现并注册进框架的运算单元，用于替换框架内置实现或引入框架不支持的操作。

三种场景需要它。性能瓶颈，某个算子在 profile 里占比很高，而框架自带实现没做融合或没针对目标形状调优。框架不支持，模型用了新的注意力变体、特殊采样逻辑，或者需要跨算子融合的复杂算子。硬件适配，目标芯片框架没提供实现，必须自己写。

替代方案的优先级很重要。先看框架有没有 torch.compile 这类自动融合、有没有官方扩展库提供的算子、能不能用 Triton 这种更易维护的方式写。手写 CUDA 应该是最后一招，不是第一招。

### 6.2 自定义算子的实现流程和坑？

五步。定义接口，确定算子签名、输入输出张量的形状与 dtype 约定、是否支持动态 shape、要不要反向。实现内核，用 CUDA 或 Triton 写计算逻辑，处理边界条件（非整除的尾块）、线程块大小与共享内存使用、访存合并。注册到框架，导出成 Python 可调用的算子，同时注册到推理后端，这一步往往最麻烦，涉及算子 schema、类型推导、shape 推导。数值验证，必须与参考实现（通常是朴素的 PyTorch 版本）做逐元素误差比对，覆盖各种边界形状。性能验证，profile 对比确认确实更快，而不是被内存搬运或其他开销吃掉。

常见坑有四个。数值精度差异，用了 float 累加导致精度不足、或者用了近似指令而业务不能容忍。动态 shape 支持不全，只测了训练时的形状，线上换个 batch 就崩。内存对齐与越界，偶发、难复现、极难调试。不同硬件架构的兼容性，在新架构上编译或性能异常。

最后一条建议：自定义算子必须有 fallback 路径，不支持当前形状或设备时能退回框架实现，否则一次升级就可能让整个服务起不来。

### 6.3 性能指标有哪些？它们怎么互相牵制？

四个。延迟是单个请求从到达到完成的耗时，必须看 P50/P95/P99，均值会掩盖长尾，而用户体验由 P95、P99 决定。吞吐是单位时间处理的任务数或 token 数，直接决定成本。硬件利用率包括算力利用率和显存带宽利用率，是判断优化还有没有空间的关键。功耗决定机架电力和散热预算，在边缘设备上尤其关键。

它们的关系是一条基本曲线：延迟与吞吐此消彼长，提高 batch 能提吞吐但会增加单请求延迟，所以工程上必须在 SLO 约束下追求吞吐最大化，而不是无约束地优化任一指标。这几者与功耗也互相牵制，为了降延迟而提高频率会拉高功耗和发热，进而触发降频，长期性能反而更差。

### 6.4 基准和 SLO 是不是一回事？

不是。基准是当前系统在标准条件下的性能数据，描述现状；SLO 是对用户承诺的服务质量目标，描述要做到什么。

建立基准要求条件可复现：固定模型版本、硬件配置、输入分布、并发模式，否则不同时间测的数据不可比。SLO 一般写成"P95 端到端时延不超过 3 秒、可用性 99.9%、错误率低于 0.5%"这种形式。流程是先测基准，再结合业务容忍度和成本预算定 SLO，然后在 SLO 约束下找系统的最优工作点，最后设监控与告警阈值，通常设在 SLO 的 80% 处作为预警线。

大模型还有特殊指标要单独承诺：首 token 时延影响"是否感觉在响应"，每 token 时延超过约 100ms 用户会觉得卡，以及流式输出的首字节时延。这些没法用单一的"端到端时延"替代。

### 6.5 性能剖析该从哪一层下手？

分两个层次。系统级工具看整条时间线、找"哪里在等"，Nsight Systems 能显示 CPU 与 GPU 的时序、内核间隙、数据传输与计算是否重叠、有没有被同步操作卡住，PyTorch Profiler 的 trace 模式做算子级时间线、stack 模式追溯调用栈找到是哪个 Python 代码触发了这个算子。内核级工具看单个算子在硬件上怎么跑，Nsight Compute 分析占用率、访存效率、bank conflict、指令吞吐，用来判断某个算子还有多少优化空间。

排查流程是四步。先确认瓶颈类型，用利用率判断是算力瓶颈、带宽瓶颈还是时延瓶颈。再看时间线的空隙，GPU 空闲区间往往意味着调度问题（批处理没做好、CPU 预处理太慢、同步点过多），而不是算子慢。然后再看单个算子的效率，这是最后一步，因为大部分性能问题不在算子实现而在系统组织。最后做假设验证，一次只改一个变量，用基准数据对比。

三种采集范式的取舍是：采样开销最小但可能漏掉短暂事件；插桩精度高但侵入代码；全量追踪信息最全但数据量大且显著影响性能，只适合离线诊断。

## 七、端侧、边云与运维

### 7.1 端侧推理框架怎么选？

主流有 NCNN（腾讯开源，移动端优化好、依赖少）、MNN（阿里，支持多后端与训练）、TFLite（Google 生态，与 TensorFlow 流程打通）、Core ML（Apple 平台，能调用 ANE）、ONNX Runtime Mobile（跨平台，模型复用方便）。

选型要看的东西其实不多：平台覆盖，只做 iOS 用 Core ML，跨 Android 和 iOS 用 NCNN 或 MNN；算子支持度，端侧框架的算子覆盖远不如服务器框架，模型里有的算子不支持就得改模型结构；体积与依赖，端侧对 App 包体敏感，框架本身的体积和动态库依赖很重要；量化支持，端侧几乎必须量化，框架对 INT8、INT4 的支持质量直接决定性能。

与服务器框架的关键差异在于，服务器追吞吐，端侧追的是单次时延加内存峰值加功耗加框架体积，甚至"模型能不能装进 App"本身就是硬约束。

### 7.2 端侧模型的常见优化手段？

六种。量化是第一优先级，INT8 或 INT4 直接减少访存和计算量，但端侧 NPU 对量化格式的要求比 GPU 更严格，很多只支持对称量化或特定粒度。模型结构简化，用深度可分离卷积、更小的隐藏维度、更少的层。算子融合与内存复用，端侧内存峰值是硬约束，必须做复用规划，避免峰值超限被杀进程。硬件加速后端，优先用 NPU 或 GPU 而不是 CPU，各框架都有对应的 delegate 或 backend 配置，配错了性能差十倍是常见问题。降精度和降分辨率的权衡，输入分辨率对时延的影响是平方级的，很多时候降一点分辨率加换更小的模型比优化大模型更有效。懒加载与预热，模型首次加载和首次推理有显著额外开销，需要在 App 启动或空闲时预热。

端侧特有的坑是不同机型芯片差异极大，同样的模型在不同手机上性能可能差数倍，必须做机型分级、分档下发不同模型版本。

### 7.3 国产加速卡上部署要注意什么？

有几件事必须提前确认，否则后面全是坑。

软件栈生态差异，CUDA 之外还有华为昇腾的 CANN、寒武纪、百度昆仑、海光等各自的计算库与编译器，成熟度、文档质量、社区活跃度都有明显差距，踩坑后能搜到的资料少，这是最大的隐性成本。算子覆盖不全，常见结构通常有官方支持，但新算子、自定义算子、复杂融合算子的缺失很普遍，往往需要改写模型或等厂商支持。精度与数值行为差异，不同硬件对 FP16、BF16 的支持程度、累加精度、特殊函数的实现都不同，迁移后指标可能变化，必须重新做精度验证。性能特征不同，算力带宽比、显存容量、互联带宽都不一样，在原硬件上调好的并行策略、批大小、切分方案都需要重新调优。

实践建议是在项目早期就把目标硬件纳入可行性验证，跑通模型、实测性能、比对精度，并优先选有官方推理栈和模型库的方案，把精力留给业务而不是算子适配。

### 7.4 视频流部署比单图推理多了什么？

多出来的工程问题不少，有些比推理本身还重。

解码开销可能超过推理。高分辨率多路视频的解码是 CPU 或 GPU 的重负载，现代方案用硬件解码器卸载，否则 CPU 会被解码吃满。流转协议多样，RTSP、RTMP、HLS、WebRTC 各有适用场景，需要统一的拉流与转封装层。抽帧策略决定成本，不是每一帧都值得推理，可以按固定间隔抽帧、按时段差异触发、或者先用轻量模型筛选再用重模型确认。多路并发与批处理，几十路摄像头的帧需要聚合成 batch 才能喂饱 GPU，但跨流组批会引入时延，得取折中。色彩空间与预处理，视频帧通常是 YUV 格式，解码后转成 RGB 再送模型会引入额外拷贝，高效实现会直接在 YUV 上做预处理或让模型接受 YUV 输入。

另外还要考虑时间戳对齐与结果聚合（同一目标跨帧的去重与跟踪），以及存储与回放（事件片段留存、证据链）。

### 7.5 推理服务该监控什么？

四层。

服务层看 QPS、并发数、错误率（按类型分：超时、显存不足、输入非法）、请求排队长度与等待时间。性能层看首 token 时延、每 token 时延、端到端时延的 P50/P95/P99，以及吞吐。资源层看 GPU 利用率、显存占用与峰值、OOM 频次、CPU 与内存、网络带宽。模型层看输出长度分布、拒答率、缓存命中率、量化后精度抽检指标。

告警要聚焦在用户能感知的指标上：P95 时延超过 SLO 的 80%、错误率突增、显存接近上限、以及输出长度分布漂移。最后一条是模型行为异常最灵敏的先行信号，很多人会漏掉。另外要建立日志与追踪的关联，每个请求带唯一 ID，能串起网关到调度到模型到工具调用的完整链路，否则线上排障会变成猜谜。

### 7.6 让你设计一个 100 QPS 的推理服务，怎么答？

按澄清、估算、架构、取舍、验证五步走。

澄清约束：模型参数量和上下文长度是多少？输入输出长度分布如何？SLO 是什么？有没有灰度与多版本需求？有没有信创或私有化要求？不问清这些，任何设计都是空谈。容量估算：用带宽估算方法算单卡的理论吞吐上限，结合输入输出长度分布算出每请求的平均 token 消耗，推出需要的卡数和副本数，乘安全系数。给架构：统一网关（鉴权、限流、路由、请求 ID）、调度层（按输入长度分流、判断前缀缓存命中）、推理引擎集群（开启连续批处理、分页 KV、前缀缓存），再加一个长请求独立队列，避免长上下文把短请求堵死。讲取舍：批大小越大吞吐越高但时延越差，按 SLO 定批上限；量化能提吞吐但要验证精度；多副本提升可用性但增加成本。讲验证：用真实长度分布压测找拐点、做故障注入（单副本挂掉、显存打满）、留降级路径。

这个结构的价值在于先量化再设计，比直接背架构有说服力得多。

### 7.7 模型热更新怎么做？

不能直接重启，因为代价和时间都不可接受。一次重启要重新加载数 GB 到数十 GB 权重、重新编译预热内核、清空所有 KV Cache 与前缀缓存，冷启动可能长达数十秒到几分钟，期间请求全部失败；多副本滚动重启虽然能保可用性，但每换一个副本就损失一份容量，高负载时段扛不住。

可行方案有三类。多版本共存加网关切流，新版本以新副本启动，就绪后按权重切流量，旧副本排空后下线，最稳。权重原地替换，如果框架支持动态加载权重，可以在同一进程内换模型，省去进程启动与内核编译，但要做好显存峰值管理，新旧权重同时存在的瞬间显存会翻倍。LoRA 适配器热插拔，多版本如果只是不同微调适配器，基座共享、只换小体积的 LoRA 权重，切换成本极低，多租户场景的标准做法。

有个隐患要注意：热更新必须考虑缓存失效。换了模型但前缀缓存还是旧的，会导致输出与模型版本不一致的诡异问题。

### 7.8 多个模型要同时在线上怎么办？

三种方案。

多进程独立部署，每个模型一个独立进程或容器，各占一份显存。隔离彻底、互不影响、风险最低，缺点是显存无法共享，多个小模型也各自占一份运行时开销，卡数需求按模型数向上取整增长。单进程多模型，同一个推理进程里同时加载多个模型，共享显存池和调度器。显存与调度效率高，能做跨模型组批，但一个模型崩溃全部受影响，不同模型的依赖冲突也很难调和。基座共享加适配器，同一基座加不同的 LoRA 或系统提示词前缀缓存，把多模型降维成单模型多配置。

第三种性价比最高，适合多租户、多业务线共用同一基座的场景。选型依据是三个问题：模型是不是同族（能不能共享基座）？显存预算紧不紧？隔离性要求多高？

另外无论哪种方案都要处理资源抢占。一个模型被大量长请求占满显存时，要能限制它的最大占用配额，否则会连锁导致其他模型也 OOM。
