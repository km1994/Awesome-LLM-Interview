## 一、框架全景

### 1.1 大模型全生命周期会用到哪些框架？

按阶段分，大概是四层。

训练层负责从零训或者继续预训练，关心的核心是并行策略和显存优化，代表是 Megatron-LM、DeepSpeed、Colossal-AI，另外还有 HuggingFace 的 Accelerate 和 Trainer 这类轻量封装。微调层在训练层之上做参数高效微调和指令微调，代表是 PEFT、LLaMA-Factory、ms-swift、Unsloth、torchtune。后训练与 RL 层要做 rollout 采样和策略优化，代表是 VeRL、OpenRLHF、TRL、AReaL、slime、ROLL。推理与服务层负责把训好的模型跑起来，代表是 vLLM、SGLang、TensorRT-LLM，这一层的细节在「模型部署与推理工程篇」里展开。

不过这个分层不是严格的上下级关系。后训练框架一般会复用训练框架做模型更新、复用推理框架做 rollout，所以它更像一个编排层，把两头拼起来。想明白这一点，就能理解为什么 RL 框架的复杂度比看起来高那么多。

### 1.2 挑框架该看什么？

权重最高的是硬件匹配，然后才是功能、性能、社区。

硬件匹配经常一票否决。如果目标环境是国产加速卡，能用的可能只有厂商自研的那一两个栈，比如昇腾的 MindSpeed 和 MindIE，社区里最流行的框架反而用不上。

功能完备度看的是你需要的特性有没有。RL 框架要支持你打算用的算法，微调框架要支持你的模型结构，缺了就得自己补，成本可能超过性能收益。

性能必须用自己的模型和自己的数据实测，宣传数字一般是最优配置下测出来的，跟你的负载可能差很远。社区热度放最后，它的作用是保证出问题时有地方查、有补丁能拿，不该是决策的首要依据。

### 1.3 为什么训练框架不能直接拿来做推理？

两者的优化目标相反。

训练框架关心的是反向传播和参数更新的正确性与吞吐，它需要保留激活值、优化器状态、梯度，追求整个训练周期最短。推理框架关心的是单次前向的延迟和并发吞吐，它要处理动态 shape、请求调度、KV Cache 复用，这些都是训练框架里不存在的概念。

所以同一个模型在训练框架上跑推理，既费显存又慢好几倍。

不过这个边界在变模糊。一些训练框架开始接推理后端来加速 rollout，一些推理框架也提供了 LoRA 训练能力。选型的时候值得重新看一眼，别按老印象下判断。

## 二、训练与微调框架

### 2.1 预训练框架有哪些？怎么选？

主流是 Megatron-LM、DeepSpeed、Colossal-AI 三家，再加上各家大厂的自研框架。

Megatron-LM 的张量并行、流水线并行、序列并行这套切分做得很成熟，基本是大模型预训练的事实标准。代价是上手门槛高，代码改造量大。DeepSpeed 的强项是 ZeRO 系列显存优化和易用性，配合 Accelerate 能少改代码就跑起来，适合中等规模。Colossal-AI 在异构显存和自动并行上做过一些探索，社区相对小一些。

选型上有个粗略的判断：模型在百亿以内、卡数不多，优先 DeepSpeed；要上到千亿、需要精细切分，就得用 Megatron 或者 Megatron-DeepSpeed 组合。

### 2.2 DeepSpeed 和 Megatron 是什么关系？

不是替代关系，实际经常一起用。

Megatron 解决的是模型怎么切。张量并行切单层内的矩阵，流水线并行切层与层，序列并行切长度维度。DeepSpeed 解决的是状态怎么分。ZeRO 把优化器状态、梯度、参数按 stage 分片到不同卡上，避免每张卡都存一份完整副本。

两者维度正交，可以叠加。Megatron-DeepSpeed 就是拼起来的产物，很多大模型的训练脚本基于它。

有个细节容易踩：ZeRO-3 和 Megatron 的张量并行同时打开会互相打架，因为两者都在切参数。要共存得做额外处理。

### 2.3 微调框架怎么选？

看你是应用团队还是训练团队。

应用团队追求开箱即用，LLaMA-Factory 和 ms-swift 是首选。WebUI 配置化，支持几十种模型结构和 LoRA、QLoRA、全参，数据格式统一，能快速验证想法。要极致速度和低显存就看 Unsloth，它把常用的 LoRA 训练算子做了底层重写，单卡上速度提升明显，代价是支持的模型和配置相对窄。

训练团队需要灵活控制细节，会直接用 PEFT 加 transformers 加 Accelerate 自己搭，或者用 torchtune 这类更接近原生 PyTorch 的库。

说到底要回答一个问题：你是想快速拿到一个能用的模型，还是要完全控制训练过程。这两个目标选的框架完全不同。

### 2.4 为什么很多团队最后会自研训练框架？

一般是被具体问题逼出来的。

硬件适配是最常见的起因。目标卡社区框架支持不全，算子、通信库、显存管理都得自己补，补着补着就变成自研了。流程整合也占很大比重，开源框架解决的是单点问题，但真实训练链路涉及数据生产、断点续训、故障恢复、指标上报、模型归档，这些胶水代码量很大。与其在别人的框架上打补丁，不如自己搭一套。还有一类是性能调优，特定模型结构有特定优化空间，通用框架为了兼容性会主动放弃这些机会。

自研的代价是要长期养一个团队。所以更常见的路径是先基于开源改，等改动的比例超过某个阈值再考虑自研，一上来就重造基本都会后悔。

### 2.5 训练时的性能瓶颈一般卡在哪？

按出现频率排：通信、数据加载、显存、算子效率。

通信是分布式训练最普遍的瓶颈，尤其是在张量并行和流水线并行的交界处，以及 ZeRO-3 每次前向都要做参数收集的地方。数据加载是单机训练里最常见的，表现为 GPU 利用率周期性掉到零。显存不够会逼你用小 batch 或者开重算，间接拖慢速度。算子效率问题通常只在个别模块上出现，用 profiler 能直接定位。

排查顺序可以简化成看 GPU 利用率的形状：锯齿状就去查数据，平顶但整体偏低就去查通信，个别尖刺去查算子。

判断通信是不是瓶颈，看 MFU 更直接。如果 MFU 常年在 30% 以下，而 GPU 利用率又不是满的，多半在等通信。

## 三、后训练与 RL 框架

### 3.1 RL 框架有哪些？各自定位是什么？

主流是 VeRL、OpenRLHF、TRL、AReaL、slime、ROLL 这几家。

VeRL 是字节开源的，主打灵活性和算法复现，把 rollout 和训练解耦，支持多种推理后端和多种 RL 算法，学术界和工业界都在用，目前算是事实上的主流选择。OpenRLHF 的特点是简洁易读，基于 Ray 做调度，适合入门和快速验证，也是读 RLHF 实现的好材料。TRL 在 HuggingFace 生态里，和 transformers 无缝衔接，适合小规模实验和算法原型。AReaL 主打异步和部分 rollout，专门解决 rollout 长尾。slime 偏 SGLang 生态，ROLL 面向大规模训练。

选型的关键是看你的瓶颈在哪。要试新算法选 VeRL，要压 rollout 成本就得考虑 AReaL 这类异步方案。

### 3.2 VeRL 是同步还是异步的？训练流程是什么？

VeRL 主体是同步框架，同时也提供了异步 rollout 的能力。

同步流程是一轮一轮走。当前策略批量生成 rollout 样本，等整批采样完成，然后做优势估计、算损失、更新参数，更新完进入下一轮。中间几个模型角色要配合：actor 负责生成和更新，critic 做价值估计（GRPO 可以省掉），reward 模型或规则打分器给奖励，另外还需要一份 reference 模型算 KL。

异步的做法是把 rollout 和训练重叠起来，采样不阻塞参数更新。VeRL 支持部分异步，但要注意异步会引入策略滞后，理论上需要重要性采样去校正。

### 3.3 VeRL 里那几个 batch size 参数是什么关系？

三个参数管三个不同层级，很容易混。

`train_batch_size` 是一次参数更新用的样本数，是全局概念。`ppo_mini_batch_size` 是把这一批样本切成几块做多轮小批次更新，切得越小、更新轮数越多，越接近 on-policy，但也越容易过拟合到当前批次。`ppo_micro_batch_size_per_gpu` 是单卡单次前向能放下的样本数，纯粹受显存限制。

关系是 `train_batch_size` 能被 `ppo_mini_batch_size` 整除，`ppo_mini_batch_size` 再被卡数与 `ppo_micro_batch_size_per_gpu` 的乘积整除。搞错了框架会直接报错，而且报错信息通常写得很清楚，照着改就行。

### 3.4 同步 RL 框架的问题在哪？rollout 长尾怎么解？

问题是木桶效应。

一轮采样里不同 prompt 的生成长度差异极大，短的几十个 token，长的几千个。同步框架必须等最长的那条生成完才能开始训练，其余算力全在空转。序列越长、难度越不均，浪费越严重。实测里 rollout 常常占整个训练时间的六七成，所以这里的优化空间最大。

常见解法有几种。按长度分桶，先跑短序列把 GPU 填满，长序列单独处理。用 partial rollout，长序列生成到一半先存下来，下一轮接着生成。把 rollout 和训练放在不同卡组上并行，用异步流水线掩盖。还可以直接限制最大生成长度，把超长的截断，这条最粗暴但很有效。

### 3.5 异步 RL 框架有哪些？partial rollout 怎么做？

异步方案的代表是 AReaL，另外 VeRL 和几家自研框架也支持部分异步。

partial rollout 的思路是把一条序列的生成过程变成可中断的：生成到一定长度还没结束，就把中间状态存下来，包括已生成的 token 和对应的 KV Cache，下一轮从断点继续，而不是从头重来。这样长尾样本就不会阻塞整轮训练。

代价是策略滞后。一条序列的前半段可能是旧参数生成的，后半段用新参数，导致这条轨迹上的动作不服从同一个策略分布。所以异步框架必须配重要性采样校正，否则训练会不稳。这也是异步方案理论更高效、实际更难调的原因。

### 3.6 训推不一致是什么？怎么缓解？

指同一个模型在训练引擎和推理引擎上的输出概率对不上。

成因主要是数值差异。两个引擎的算子实现不同，比如 attention 的融合方式、归约顺序；精度配置不同，训练用 BF16 但推理侧做了 FP8 或 INT8 量化；并行切分方式不同也会导致累加顺序有差异。差异小的时候只是噪声，差异大的时候会让重要性采样比值失真，训练直接崩。

缓解手段有几个方向。尽量统一两边的精度和算子实现，比如推理侧也用 BF16、也接同一套 kernel。用重要性采样比值做裁剪，把异常比值截断。定期用训练引擎重新计算一批样本的概率做校准。有些框架会把推理侧的关键层替换成训练同款实现，牺牲一点速度换稳定性。

### 3.7 partially rollout 的框架会保存旧 policy 的 KV Cache 吗？

会，而且这是 partial rollout 能成立的前提。

如果中断时只存已生成的 token 而不存 KV Cache，恢复时就得把整段前缀重新前向一遍，那中断就失去意义了。所以要把 KV Cache 一起持久化，恢复时直接挂载。工程上的难处在于这部分缓存可能分布在多卡甚至多机上，需要额外的存储与管理机制。

还有个配套细节：保存的 KV Cache 对应的概率值也要一起存，因为后续做重要性采样校正时需要知道这些 token 是在哪个策略下生成的。如果是 MoE 模型，还要额外保存路由结果，也就是 expert 的选择，否则重算时路由可能和生成时不一致，概率就对不上了。

### 3.8 OpenRLHF 和 TRL 有什么差别？

差异在规模和易用性的取向上。

OpenRLHF 基于 Ray 做分布式调度，把 actor、critic、reward、reference 拆成独立的 Ray actor 分组，支持把不同模型放到不同卡组上，适合多机多卡的中大规模训练。代码结构清晰，读起来不费劲。

TRL 是 HuggingFace 生态的一部分，和 transformers、peft、accelerate 直接打通，API 简洁，适合单机或小集群上做算法验证。它的强项是集成度，不是规模，上生产要自己补分布式和容错。

一个比较务实的路径是先在 TRL 上把算法调通，再迁到 OpenRLHF 或 VeRL 上做规模。

## 四、Agent 框架

### 4.1 Agent 框架可以怎么分类？

按"控制流由谁决定"分成三类，这个切法最清晰。

编排类框架提供构建块，流程由开发者用代码定义，代表是 LangChain、LlamaIndex、LangGraph。多智能体类把 Agent 当作可协作的角色，内置消息传递与分工机制，代表是 AutoGen、CrewAI。平台类是低代码的可视化编排，代表是 Dify、Coze、n8n。

还有一类是模型厂商自带的 SDK，比如 OpenAI Agents SDK、Claude Agent SDK，特点是和自家模型的工具调用能力贴得更紧，但换模型时迁移成本高。

选型的核心问题只有一个：流程是确定的还是需要 Agent 自己探索的。确定就用编排类把流程写死，需要探索才上多智能体。

### 4.2 链和图在工程上差在哪？

链是线性的，执行路径在写代码时就定好了，每一环的输出交给下一环。图允许环和条件分支，下一步走哪个节点可以由上一步的输出决定，甚至由 LLM 判断，所以天然支持"反复尝试直到成功"这种模式。

这正是 Agent 需要的能力。

这个区别带来工程上的取舍。链的可预测性好、调试容易，适合确定性流程。图表达能力强但状态管理复杂，需要定义清楚状态结构和终止条件，不然很容易写出无限循环。

所以现在比较务实的分工是用图来承载 Agent 循环，用链来做循环内部的固定子流程。

### 4.3 AutoGen 和 CrewAI 怎么选？

AutoGen 偏对话驱动，CrewAI 偏角色驱动。

AutoGen 把多智能体建模成一场对话，Agent 之间轮流发言、可以调用工具、可以由人介入。适合研究和需要灵活对话模式的场景，控制粒度细但流程不够直观。CrewAI 直接给 Agent 分配角色、目标和工具，再定义任务和协作顺序，配置化程度高、上手快，适合业务流程清晰的分工场景。

两者共同的坑是 token 消耗失控。多智能体互相通信很容易产生大量冗余对话，需要给对话加摘要、设置最大轮数，并且明确定义任务完成的判据。不做这几件事，成本会失控得很快。

### 4.4 Dify、Coze 这类低代码平台适合什么场景？

适合验证想法和做内部工具，不太适合承载核心业务。

优势很实在：可视化编排、内置知识库和插件生态、多模型切换方便，一个非技术同学也能搭出可用的问答机器人，验证成本极低。拿它做 POC、做内部效率工具是合适的。

局限在于深度定制和可观测性。要接私有系统、做复杂权限控制、精细调优检索策略的时候，平台会撞到天花板。出问题排查也受限于平台的日志能力。

所以常见路径是先用低代码验证需求，确认有价值后再用代码框架重写。反过来做，先花两个月写代码再发现需求不成立，损失就大了。

### 4.5 Agent 框架依赖这么重，生产环境要注意什么？

依赖爆炸是第一位的。

Agent 框架通常带大量传递依赖，各类 SDK、向量库客户端、解析库、可观测性组件，版本冲突很常见，而且框架本身迭代快、破坏性变更不少。生产环境建议锁死具体版本，并且尽量只引入真正用到的子包。

可观测性也要提前规划。Agent 的执行路径是动态的，出问题时光看日志很难还原，需要把每步的输入输出、工具调用、耗时都结构化记录下来，最好能可视化回放。

超时和重试策略同样重要。LLM 调用本身就不稳定，加上 Agent 的多步特性，任何一步卡住都会拖垮整个请求，必须有分步超时和整体预算。

最后是权限边界。框架给的便利不能成为越权的理由，工具能做什么必须由业务侧约束，不能交给提示词去管。

## 五、选型方法论

### 5.1 一个新项目怎么挑技术栈？

从约束出发，别从流行度出发。

先把硬约束列清楚：算力在哪，是自有集群还是云、什么卡；数据能不能出域；延迟和成本预算是多少；团队熟悉什么技术栈。这些确定之后，候选范围通常会缩到两三个。然后做小规模实测，用真实数据对比候选方案的关键指标。最后再看社区活跃度和文档质量，它是长期维护成本的一部分，但不该是决策的首要依据。

有个反直觉的建议：项目早期优先选自己能改得动的框架。因为你一定会遇到需要打补丁的地方，改不动的框架会变成死结。

### 5.2 什么时候该自研，什么时候该用开源？

看你的需求是通用还是专用。

通用需求，比如标准微调、标准推理、标准 Agent 流程，一律用开源，自研没有任何优势，还要额外承担维护成本。只有当需求足够特殊、开源方案要打大量补丁才能满足时，自研才划算。

判断标准可以量化成一句话：如果为了适配你的场景，对开源框架的改动量超过了你自己的代码量，就该考虑自研了。

还有一种情况不用犹豫：开源方案在架构上就不支持你的场景，比如你需要的并行策略它根本没有。

### 5.3 框架升级怎么控制风险？

把升级当成一次有风险的发布来对待。

先锁定当前版本并记录完整依赖树，保证随时能回退。升级前在离线环境跑一遍回归评估集，对比关键指标有没有退化。框架升级经常在数值精度和默认参数上发生静默变化，这类问题不跑评估集根本发现不了。然后在非核心业务上灰度，观察一个周期再全量。整个过程保留新旧两套环境，不要原地覆盖。

最需要留意的是默认行为变更，比如默认精度、默认模板格式、默认的 loss 归一化方式。这几处改动最隐蔽，也最容易踩。

### 5.4 怎么判断一个开源框架值不值得长期投入？

看四件事：谁在维护、迭代节奏、破坏性变更的频率、以及出走成本。

维护方如果是公司，比如字节、阿里、HuggingFace，通常意味着有商业场景在背后驱动，相对稳定；纯个人项目要谨慎。迭代节奏看最近半年的提交频率和 issue 响应速度。破坏性变更的频率反映维护方对兼容性的态度。

出走成本最容易被忽略。要看你的代码和框架耦合得多深，如果到处都是框架特有的抽象，换框架就等于重写。

还有个很实用的观察指标：框架有没有清晰的版本策略和迁移指南。连这个都不提供的，长期投入风险很高。
