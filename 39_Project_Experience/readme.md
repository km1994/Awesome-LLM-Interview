## 一、项目该怎么讲

### 1.1 面试官问项目，真正想确认什么？

表面上是在核对你简历上的描述，实际是在确认三件事：这件事你动过手没有、遇到问题时你的判断链条是什么、以及你的能力边界在哪。

有个现象挺普遍：简历写得很漂亮，但能把 Agent 讲清楚的人一只手数得过来。追问两三层就露底的，通常不是能力差，而是只做了执行、没做过判断。所以准备项目的时候先问自己一句，这个决策当时是我拍的吗，依据是什么，还有哪些选项被我否了。

### 1.2 一个项目按什么顺序讲最稳？

业务问题、约束条件、方案选型、落地细节、量化结果、复盘反思。

前面几步加起来用不了一分钟，但它们决定了对方后面有没有兴趣听。很多人一上来就讲技术方案，面试官不知道你在解决什么问题，后面所有细节都无从评价，最后只能靠打断你来问。

复盘那一段别省。说清楚哪些地方事后看能做得更好，比把项目讲成完美案例可信得多。面试官见过太多完美案例了。

### 1.3 为什么"项目细节拷打"才是主战场？

社招面试的结构基本是项目细节拷打、穿插八股、再考代码。八股和代码都是可以提前准备的固定项，真正能区分出"做过"和"读过"的只有项目细节。

常见的拷打路径是：数据从哪来、为什么这么切分、指标怎么定的、上线后哪一类 badcase 最多、这个问题你当时怎么定位的。每一问都直指执行细节，背不出来。

反过来想，这也是最容易准备的部分。把项目里每个数字、每次实验、每个决策的依据都回忆清楚，比多刷二十道八股划算得多。

### 1.4 简历上的项目怎么写才扛得住追问？

判断标准只有一条：写上去的每一条，你都得能展开讲十分钟。

具体写法是每条描述都带上做了什么、用什么方法、拿到什么结果，避开"负责某某模块"这类没有信息量的句式。如果你只参与了外围，就别往上写，或者明确标出你负责的边界在哪。面试官不介意你做得浅，介意你含糊。

还有个小技巧：简历可以随着面试反馈动态调整。一开始 Agent 那块我做得浅，就没写；后来发现问得多而且热，补上去之后 Agent 方向的岗位也有面试机会了。简历不是一次定稿的东西。

### 1.5 项目没有亮点怎么办？

大部分业务项目在技术上确实谈不上创新，这很正常。但每个项目都有约束下的选择：为什么这里用 RAG 而不是微调、为什么选这个模型、为什么接受了这个精度损失。

把这些权衡讲透，亮点就出来了。面试官想听的不是你用了多新的技术，而是你在限制条件下做了什么判断。

另一种情况是真的做得很浅。那就诚实说明边界，然后把真正负责的那一小块讲深。判断人的标准是深度，不是广度。

## 二、数据与训练细节

### 2.1 训练集和测试集是怎么来的？

要能说清数据来源、清洗规则、标注方式、划分策略这四件事。

来源通常是业务日志、公开数据集、模型合成三类混着用，各自占多少、为什么这么配比，得能解释。清洗规则要具体到方法：去重用的什么、长度怎么过滤、噪声样本怎么剔除。标注方式决定数据质量的上限，人工标注要能报出一致率，模型合成要能说出用的哪个模型、过滤策略是什么。

划分上最容易出问题的是同源样本泄漏。同一篇文档的不同段落分别进训练和测试，模型看起来泛化很好，其实是记住了原文。测试集如果是从训练数据里切的，还得说明做过什么去重和污染检查。

### 2.2 指令微调的数据格式有哪些坑？

不同框架要求不一样，但有三类坑是共通的。

训练模板和推理模板必须严格一致，多一个空格或者少一个换行，效果就能掉一截。这是最隐蔽也最常见的问题，换框架的时候一定要重新确认一遍。

第二个是指令部分不该计入损失。只有回答部分参与计算，写错了等于让模型学着重述问题。第三个是多轮对话的损失口径，一般只算最后一轮的回答；把历史轮次也计进去，模型会学会"复述历史"这个坏习惯。

这三条在不同框架里的默认行为不同。所以别默认它是对的，去读源码或者看文档确认。

### 2.3 强化学习的数据格式要注意什么？

RL 的数据比 SFT 简单，通常只需要 prompt 和用于判分的标准答案，不需要参考答案文本。要注意的地方主要在三处。

奖励函数需要的信息必须齐全。如果奖励依赖参考答案做精确匹配，数据里就得带答案字段；如果奖励依赖代码执行，测试用例也得一并提供。这些字段缺一个，训练就跑不起来。

prompt 的多样性要够。GRPO 一次 rollout 多个样本，如果同一个 prompt 反复出现，组内奖励方差会趋近于零，优势估计就失去意义了，那一批样本等于白采。

难度分布要有梯度。全是简单题会提前饱和，全是难题则奖励恒为零，两种情况都学不到东西。

### 2.4 数据量不够的时候你怎么办？

按性价比往下排。

先看能不能复用。基座模型已经具备的能力不必再训，只补它缺的那一块，这样数据需求能砍掉一大截。然后做数据增强，但要小心增强引入的新错误模式，增强出来的样本自己得先验一遍。再往后是用强模型合成数据，人工或规则过滤，这是目前最常用的扩容手段。

如果这些做完还是不够，那该重新想一下任务本身是不是不该用微调解决。有些问题换成 RAG、提示工程，或者干脆加一层规则后处理，效果反而更稳，维护成本也低。

### 2.5 改过损失函数吗？为什么要改？

这题问的是你有没有动过手，不是考公式。

能答的场景有几类。业务上把某些错误定义得更严重，于是在损失里给对应样本加权。多任务训练时不同任务的量纲差异大，需要做归一化或者动态调权。生成任务想约束输出格式，加一个辅助损失项。回答的时候记得带上改了什么、为什么这么改、指标怎么动的。

如果确实没改过，别硬编。可以说清楚你评估过但最终没改的理由，比如改动带来的收益还不如直接调数据配比。这种判断本身也是加分项。

### 2.6 基于规则的奖励函数怎么设计？

核心工作是把"什么是好回答"拆成机器能判的原子条件。

数学题按最终答案精确匹配，代码题跑单元测试算通过率，格式题用正则或者 JSON 解析校验，工具调用题检查参数和调用序列。奖励可以是这些条件的加权和，但权重得小心，给偏了模型会专攻那一个条件，其他全不管。

规则奖励的好处是干净、可复现、不容易被刷，坏处是覆盖面窄，只有可验证任务能用。所以常见做法是分开处理：可验证的部分走规则，开放的部分交给模型判分，模型判分那部分再用人工抽检校准。

## 三、过拟合、泛化与幻觉

### 3.1 项目里遇到过哪些过拟合现象？怎么定位的？

最典型的是泛化到措辞。训练集里的问法怎么问都对，换个说法就崩，这说明模型学的是模板，不是能力。

定位方法是两条线一起看。一条是训练集和验证集的损失曲线，另一条是人工抽样看 badcase 的类型。如果错题集中在训练集里没出现过的句式上，基本可以定性了。还有个信号是输出风格高度单一，回答的开头和结尾都长得一样。

处理办法里最有效的其实是补数据，其次才是降训练轮数、减小学习率、加更多样的指令模板。加正则往往是最不划算的那个选择。

### 3.2 微调之后通用能力掉了，怎么办？

先量化，再动手。

用通用能力评估集跑一遍微调前后的对比，看掉的是知识、推理，还是格式遵循。不同维度对应不同解法，不测清楚就动手容易白费功夫。

常见对策有三种。训练集里按比例混入通用语料，这个最有效。换更大或更强的基座，抗遗忘能力更好。或者干脆改成全参微调而不是 LoRA，有研究表明全参在部分场景下遗忘反而更少。

报结果的时候要把业务收益和通用能力保持率一起给出来。只报前者等于把代价藏起来了，这种汇报方式在评审里很容易被挑出来。

### 3.3 用了哪些手段增强泛化能力？

数据层面的手段优先级高于模型层面。

多做指令模板的多样性，让同一个语义有十几种问法。调整数据配比，别让某一类任务占比过高。引入负样本，把"不知道"也当成一个正经答案教给模型。多任务联合训练也管用，任务之间能互相起到正则作用。

模型层面就是控制训练轮数、加权重衰减，Dropout 在大模型上用得不多。

另外要警惕一种假泛化。模型在同类测试集上表现很好，可能只是因为构造测试集时用了和训练集一样的模板。这种"泛化"一上线就原形毕露。

### 3.4 幻觉怎么从欠拟合和过拟合两个角度分析？

这个拆法挺有用，因为它直接指向两套不同的解法。

欠拟合型幻觉是模型没学会。知识本身没进参数，或者进去了但不会用。表现是对训练数据里充分覆盖的内容也答错，复述材料都能复述错。解法是补数据、加训练量，或者在推理时把材料直接喂进上下文。

过拟合型幻觉是模型学过头了。它学会了"回答必须像模像样"这个模式，于是没依据的时候也要编。表现是对没见过的实体也能给出很自信的细节。解法是加拒答样本、做偏好优化惩罚无据回答，并提高上下文的信息质量。

面试里能主动区分这两类，比罗列一堆缓解手段更有说服力。

### 3.5 有没有做过自动化识别幻觉？

常见做法是让模型拆解自己的回答。

把输出切成原子陈述，逐条检索证据做匹配，统计无支撑陈述的比例。证据可以是外部知识库，也可以是题目给定的上下文，后者就对应 RAG 场景里的忠实度评估。再用另一个不同族系的模型做交叉判分，避免自我偏好。

成本更低的做法是先用规则筛一遍。回答里出现了给定材料中不存在的数字、日期、人名，直接标红送人工。这类特征在事实性错误里占比很高，能覆盖大部分风险，而且几乎不花钱。

## 四、评测与验收

### 4.1 测试集和评测指标是怎么定的？

测试集从真实业务日志里采样，覆盖高频场景、长尾难题和负样本三类，每条都带标准答案或评分细则。

指标要分层。检索类用 Recall@k 和 NDCG，生成类用人工或 Judge 打分，端到端用任务成功率或人工可用率。单一指标几乎总是会误导人，所以至少要配一个反向指标，比如在准确率提升的同时，看看拒答率有没有异常升高。

上线前把评估集固化成回归测试，每次改动自动跑，只关心有没有退化。这一步不做，后面每次改动都是一次赌博。

### 4.2 微调效果怎么评估？

通用能力、生成能力、人工评估，三层各看一遍。

通用能力用公开基准或自建通用集，确认没有明显退化。生成能力用业务评估集，看准确率、格式遵循、拒答边界。人工评估看输出质量，因为分数不变不代表体验不变。模型可能变得啰嗦，可能输出变短，也可能中英文混杂，这些自动指标都捕捉不到。

三层都要报，而且门槛要提前定。明确哪一项掉了就不放行，比事后争论要不要上线省事得多。

### 4.3 离线指标涨了线上没涨，怎么排查？

按分布、口径、样本量、业务链路这个顺序查。

最常见的是分布差异。离线测试集的问法比线上规整，线上却有大量多轮追问、错别字、无关输入，这些模型都没在离线集上见过。其次是口径不一致，离线的"准确"和业务定义的"可用"可能压根不是一回事。样本量不足也会造出假象。最后要检查业务链路，问题可能出在模型之外，检索质量、前端展示、超时降级都会影响最终效果。

排查方法很直接：把线上的真实请求采样下来，直接喂给模型做离线复现。如果离线表现依然好，那就不是模型的问题。

### 4.4 怎么给一个项目做整体效果评估？

先定义成功标准，再谈指标。

成功标准来自业务，比如人工接管率降到多少、用户追问率降到多少、单次成本压到多少。这些定下来之后再往下拆成可测的技术指标，建立基线和门槛。

评估时用同一套输入对比新旧方案，其他变量都冻住。结果要给出置信区间，或者至少说明样本量。只说"提升了 12%"却不说在多少样本上测的，说服力很弱，评审时也容易被追问。

## 五、落地难点

### 5.1 大模型在业务里难落地，主要原因有哪些？

技术原因只占一部分，更常见的拦路石在技术之外。

效果不稳定是最直接的。同样的输入偶尔给出质量不同的输出，这在要求确定性的业务里很难接受。其次是难以归因，出了问题说不清是模型、检索还是数据的问题，排查成本高。

业务侧的阻力也不小。投入产出算不过来，合规风险不明，而且往往缺少合适的评测手段来证明价值。

应对上，效果波动可以靠约束解码、校验重试、结果后处理收敛。归因问题靠分层评测加日志追踪。价值证明靠小范围灰度，先拿到可量化的收益再谈扩围。

### 5.2 效果、成本、时延怎么权衡？

三者不可能同时最优，所以先把业务底线定下来，再去优化剩下的。

常见做法是分层。简单请求走小模型或规则，复杂请求才升级到大模型。非实时场景用批处理摊薄成本。实时场景优先保证首 token 时延，牺牲一点输出长度。

还有一条路是压缩输出。很多场景用户只看前几句话，把输出长度限制住，成本能降一半以上，体验几乎不受影响。

这类判断必须在项目早期跟业务方确认。等到方案定型再改，会很被动。

### 5.3 讲一次失败的经验，怎么讲才不减分？

选一个"技术上失败但认知上有收获"的案例，别选推责型的。

结构是：当时的目标、我判断的依据、实际发生了什么、我什么时候意识到判断错了、后来怎么调整、如果重来会怎么做。重点在那个"什么时候意识到"，它体现的是排查能力，不是运气。

有两种讲法要避开。一种是失败全靠外部原因解释，听起来像在推锅。另一种是把失败包装成成功，比如"虽然指标没涨，但积累了宝贵经验"，这种话面试官一听就知道你不愿意承认。

### 5.4 安全合规场景有什么额外要求？

数据不出域、输出可追溯、权限隔离，这三条是主要的。

数据不出域意味着可能只能用私有化部署的开源模型，模型选型和算力预算都得重新算。输出可追溯要求每个回答都能定位到证据来源，这会反过来约束技术方案，纯生成式在这里基本行不通，必须带检索。

权限隔离最容易被忽略。Agent 能查库，但它不该查到当前用户无权访问的内容，而且这个隔离得在检索阶段完成，不能靠提示词去拦。提示词拦截看着省事，一旦被绕过就是数据事故。

内容安全兜底和审计日志也要做，输入输出两侧都得过滤。

### 5.5 怎么让业务方接受效果的不确定性？

把不确定性量化出来，别掩盖它。

给出准确率和错误率的分布，说清哪类问题一定会出错、出错之后兜底是什么。如果方案里设计了人工介入或者二次确认，业务方的接受度会明显提高。

另一个有效手段是先用有确定收益的场景试点。比如把重复度最高的咨询自动应答，人工只处理复杂 case。拿到数字之后再谈扩围，比一上来就推销全自动方案务实得多。

## 六、开放题答题框架

### 6.1 "发现问题→分析→解决"的通用答题框架

这类题出现频率最高，也是没经验最难答的一类。

框架分四步。先说现象，要具体到指标和量级，别只说"效果不好"。再说假设，列出两三个可能的原因，各自说明如果成立会看到什么表现。然后是验证，讲你用什么方式排除或者确认每个假设，这一步最能体现方法论。最后是处理与复验，改完之后怎么确认问题真解决了、有没有引入新问题。

举个能用的例子。发现奖励分持续上升但人工评估不涨，于是去查奖励函数哪里有漏洞，发现模型学会了输出特定格式来骗分。改成多信号组合奖励并加人工抽检之后，奖励分回落，人工评分上去了。这种案例比空谈"要注意 reward hacking"有说服力得多。

### 6.2 怎么答"设计一个 XX 系统"这类题？

先澄清，再算量，然后给架构，最后讲取舍和验证。

澄清阶段问清用户规模、延迟要求、数据情况、有没有合规约束。算量是用粗略估算把规模定下来，比如请求量和单次 token 消耗决定需要多少算力。架构要分层给，从入口到核心到兜底，每层说清职责。取舍要主动讲你放弃了什么、为什么可以放弃。验证说明清楚上线前怎么测、上线后看什么指标。

千万别一上来就报框架名。面试官想听的是判断，不是工具清单。

### 6.3 面试官视角：什么样的候选人会被录用？

能说清"为什么"的人。

同样是做过 RAG，一个人说"我用了向量检索加重排"，另一个人说"我一开始只做向量检索，发现专有名词召回很差，加了 BM25 混合检索之后 Recall@5 从 0.62 涨到 0.81，再上 Cross-Encoder 重排把 NDCG 又提了 8 个点"。后面这位会被记住，而且几乎不用再追问。

另一点是诚实。被问到没做过的部分，直接说没深入做过，但可以讲讲理解。面试官一般都听得出来硬编，而硬编是减分最狠的一种。

### 6.4 被问到不会的问题怎么办？

先确认问题边界，再给思路，最后承认不确定。

可以说"这个问题我没在生产里遇到过，我的理解是取决于某某条件，如果要落地我会先验证某某"。这种回答展示了推理能力，比沉默或者硬答都好。

如果是完全没听过的名词，大方承认没接触过，然后试着从已知的东西去推断。比如没做过某个 RL 算法，可以类比到熟悉的 PPO，说清差异点在哪。面试官对知识盲区通常很宽容，对胡编很敏感。
